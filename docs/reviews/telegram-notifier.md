# Review checklist: telegram-notifier

Reviewed by: QA, Security, Adversarial, Architecture/quality (4/4 complete).
Files in scope: `cmd/telegram-notifier/main.go`, `cmd/telegram-notifier/handler.go`, `cmd/telegram-notifier/handler_test.go`, `cmd/telegram-notifier/Dockerfile`, `deploy/k8s/telegram-notifier.yaml`.

I read the current `main.go` in full to check the adversarial/architecture reviewers' two "critical shutdown" claims before trusting them — one turned out to be based on a wrong assumption about the NATS client API (see "Reviewed — finding rejected" below). Everything else here is confirmed against the real code.

## To fix

- [ ] **Liveness probe cannot work — container has no shell** — `cmd/telegram-notifier/Dockerfile` builds the final stage `FROM scratch` (no shell, no binaries besides the Go binary), but `deploy/k8s/telegram-notifier.yaml:39-46` defines an exec liveness probe running `kill -0 1` via `sh -c`. `sh` does not exist in the image. This probe will fail every single time it runs, which means Kubernetes will treat the pod as perpetually unhealthy and restart-loop it in a real cluster. **This is a deployment-breaking bug**, not a style nitpick — flagged independently by 4 separate reviews (architecture-telegram, QA-telegram, security-shared-infra, adversarial-shared-infra). **Fix:** switch the final Dockerfile stage from `scratch` to `alpine` (matching the pattern already used by `web-ui-api`'s Dockerfile), keeping the non-root user and `ca-certificates` for the Telegram HTTPS calls, so the exec probe has a shell to run.

- [ ] **`msg.Metadata()` failure path never terminates or reports failure** — `cmd/telegram-notifier/main.go:174-190`. When `msg.Metadata()` errors, the code always does `msg.NakWithDelay(10 * time.Second)` and returns — there's no delivery-count check, so on the final allowed attempt it neither calls `msg.Term()` nor publishes `notifications.failed`. JetStream's own `MaxDeliver=5` will still eventually stop redelivering the message at the broker level (so it's not literally infinite), but the practical effect is worse in a different way: the notification silently stays "pending" forever in the database with no operator-visible failure, since nothing ever publishes to `notifications.failed` for this path. **Fix:** read the delivery count via `msg.Headers().Get("Nats-Num-Delivered")` as a fallback (this doesn't require `Metadata()` to succeed), and when it's ≥ `streams.EventsConsumerMaxDeliver`, publish `notifications.failed` and call `msg.Term()` instead of naking again — mirroring the pattern already used lower in the same function for the Telegram-send failure path.

- [ ] **`ConsumeContext` from `consumer.Consume()` is discarded** — `cmd/telegram-notifier/main.go:88-109`. `_, err := consumer.Consume(...)` throws away the returned `ConsumeContext`. Note: `Consume()` itself is non-blocking (it registers the callback and returns immediately) — the code's structure of calling it and then blocking on `<-ctx.Done()` is correct, contrary to what two of the reviews claimed (see rejected finding below). But because the `ConsumeContext` is discarded, there's no way to explicitly stop new message delivery before `nc.Close()` runs on shutdown — the connection just gets yanked out from under any in-flight callback, which can lose an ack that was about to go out (causing a duplicate delivery on restart). **Fix:** capture the `ConsumeContext` (`consumeCtx, err := consumer.Consume(...)`) and call `consumeCtx.Stop()` right after `<-ctx.Done()` returns, before the deferred `nc.Close()` runs, so message delivery stops cleanly first.

## Worth fixing, lower priority

- [ ] **Telegram HTTP timeout equals `AckWait` exactly** — `cmd/telegram-notifier/handler.go:72` sets a 30s client timeout, and the consumer's `AckWait` (`internal/streams/streams.go`) is also 30s. A slow-but-successful Telegram response leaves ~0 seconds of margin to publish `notifications.sent` and ack before JetStream considers the message timed out and redelivers it — which, combined with the in-memory dedup cache below, is one of the few realistic paths to an actual duplicate Telegram send. **Fix:** lower the Telegram client timeout to ~15-20s to leave a real margin.

- [ ] **Publishes to `notifications.sent`/`notifications.failed` carry no `Nats-Msg-Id`** — `cmd/telegram-notifier/main.go:319-358` (`publishNotificationSent`, `publishNotificationFailed`). Unlike the `events.discovered` publish (which dedups on event ID), a retried publish here has no dedup key, so a publish-retry-after-partial-failure can create two `notifications.sent`/`.failed` rows in Turso for the same delivery attempt. **Fix:** add `jetstream.WithMsgID(...)` using something stable per attempt, e.g. `fmt.Sprintf("sent-%d-%d", eventID, natsSeq)`.

- [ ] **Backoff comment says "exponential", implementation is linear** — `cmd/telegram-notifier/handler.go:38`. `delay := time.Duration(numDelivered) * 5 * time.Second` is linear (5s, 10s, 15s...), not exponential. Design.md only requires "explicit backoff", so the linear implementation itself is fine — just fix the comment to stop mischaracterizing it.

## Reviewed — accepted as a known limitation, not fixing

- [ ] **In-memory `recentlySent` dedup cache doesn't survive a process crash/restart.** Verified real: the cache is written *before* the NATS publish+ack (`main.go:246-252`, ahead of the publish at line 255 and the ack at line 282) specifically so a same-process redelivery (publish failed, message renaked) doesn't re-send to Telegram. But if the process crashes between a successful Telegram send and the ack, the message is redelivered after restart with an empty (new-process) cache, and a duplicate Telegram message goes out. **Reordering the cache-write relative to the ack would not fix this** — the cache is memory-only, so it's empty after any restart regardless of write order; a real fix would mean persisting dedup state to Turso transactionally before ack, which is a bigger design change than a bug fix. Recommend adding a one-line code comment documenting this as an accepted trade-off (rare: crash-exactly-between-send-and-ack) rather than delegating a "fix" that can't actually close the gap.

## Reviewed — finding rejected (reviewer was wrong)

- [x] **"`consumer.Consume()` blocks, so `<-ctx.Done()` is unreachable and shutdown hangs"** — claimed by both the adversarial-telegram-notifier and adversarial-shared-infra reviews. I read `main.go:88-109` directly: `jetstream.Consumer.Consume()` is documented and implemented as **non-blocking** — it registers the callback, spawns its own internal goroutines, and returns immediately. The code's actual structure (call `Consume()`, then block on `<-ctx.Done()`) is the correct, intended usage pattern, not a bug. The real gap here is narrower — see "discarded `ConsumeContext`" above, which I kept.

## Reviewed — no action needed

- [x] Consumer policy (durable name, `MaxDeliver=5`, `AckWait=30s`), message schemas, HTML-escaping of Telegram message content, secrets sourced from `Secret` objects (not hardcoded), non-root container, retrigger/redelivery interaction with `natsSeq` cache-bypass — all confirmed correct.
