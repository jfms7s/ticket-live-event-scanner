# Review checklist: web-ui-api

Reviewed by: QA, Security, Adversarial, Architecture/quality (4/4 complete).
Files in scope: `cmd/web-ui-api/main.go`, `cmd/web-ui-api/database.go`, `cmd/web-ui-api/handlers.go`, `cmd/web-ui-api/main_test.go`, `cmd/web-ui-api/Dockerfile`, `deploy/k8s/web-ui-api.yaml`.

I read `database.go` and `main.go` in full before writing this, since three reviewers independently called the retrigger bug "critical" — worth checking exactly how bad it actually is (it's real, but narrower than the reviews suggest — see below).

## To fix

- [x] **Manual retrigger silently no-ops while a notification is still `pending`** — `cmd/web-ui-api/database.go:48-63` (`upsertEventAndInsertNotification`). The idempotency check (`SELECT COUNT(*) ... WHERE event_id = ? AND status = 'pending'`, line 52) skips inserting a new row whenever *any* pending notification exists for the event — it doesn't check whether the incoming message is `disc.Reason == event.ReasonDiscovered` (a redelivery, which is what this check is meant to protect against) or `event.ReasonManualRetry` (a deliberate user action, which design.md §6.4 says should always create a fresh pending row). Confirmed narrower than the reviews claimed: retriggering a `sent` or `failed` notification works fine today (they don't count toward `existingCount`), since the bug only fires when the existing notification is still literally `pending` — e.g. a user hits "retrigger" on something that's stuck in-flight. Still a real, spec-contradicting bug for that case. **Fix:** only apply the skip-if-pending check when `disc.Reason == event.ReasonDiscovered`; when `disc.Reason == event.ReasonManualRetry`, always insert. This also incidentally removes the narrow check-then-insert race a reviewer flagged (see "Reviewed — downgraded" below), since the manual-retry path stops needing the check at all.

- [x] **web-ui-api's own NATS consumers have no `MaxDeliver`/`AckWait`** — `cmd/web-ui-api/main.go:173-177` and `193-197` (`createOrUpdateWebUIEventsConsumer`, `createOrUpdateWebUINotificationsConsumer`). Both `ConsumerConfig`s set only `Durable`, `AckPolicy`, `FilterSubject` — no delivery bound. Confirmed: on a JSON unmarshal failure (`main.go:224-227`, `264-267`, `277-280`), the code calls `msg.Nak()` with no cap, and since these consumers default to unlimited redelivery, a single malformed message naks forever, occupying the (single, sequential) consumer loop and blocking every message behind it. **Fix:** two changes — (a) add explicit `MaxDeliver`/`AckWait` to both `ConsumerConfig`s (match `streams.EventsConsumerMaxDeliver`/`AckWait` from the shared package for consistency), and (b) for JSON-unmarshal failures specifically, use `msg.Term()` instead of `msg.Nak()` — a malformed message will never become parseable on retry, so retrying it is pure waste.

- [x] **Consumer goroutines use `context.Background()`, ignoring the app's shutdown context** — `cmd/web-ui-api/main.go:208` and `244` (`consumeEventsDiscovered`, `consumeNotifications`) each create their own `context.Background()` instead of receiving the cancellable `ctx` built in `main()` (line 55). On SIGTERM, `main()` only gracefully shuts down the HTTP server (line 158-162) and then returns — these two background goroutines get killed abruptly by process exit with no chance to stop cleanly, which can abandon a message mid-processing (already-processed-but-unacked, causing a duplicate on restart). **Fix:** pass `ctx` into both functions; have a small watcher goroutine call `msgsChan.Stop()` when `ctx.Done()` fires, so the blocking `msgsChan.Next()` unblocks with an error and the loop exits before the process terminates.

## Worth fixing, lower priority

- [x] **`fmt.Printf` instead of `log.Printf`** — `cmd/web-ui-api/database.go:149`. The `updateNotificationSent` equivalent (line 117) correctly uses `log.Printf`; `updateNotificationFailed` doesn't, so that message bypasses whatever log routing/aggregation is set up in production. One-line fix.

- [x] **Dockerfile has no explicit `USER` directive** — relies solely on the Kubernetes `securityContext.runAsUser: 1000` for non-root execution. Works as deployed, but the image itself defaults to root if ever run outside that specific manifest (local `docker run`, a different orchestrator). **Fix:** add `USER 1000:1000` in the Dockerfile as defense-in-depth, matching what the manifest already enforces.

- [x] **Retrigger publish uses the inbound HTTP request's context** — `cmd/web-ui-api/handlers.go:164` passes `r.Context()` to `app.js.Publish(...)`. If the client disconnects mid-request, the context cancels; depending on timing the NATS publish may still succeed server-side while the client sees a 500 and is tempted to retry, potentially double-publishing a retrigger. Low-likelihood edge case. **Fix (optional):** use a short-lived detached context (`context.WithTimeout(context.Background(), 5*time.Second)`) for the publish call specifically, decoupling it from the client's connection lifecycle.

- [x] **`derefString` turns a `nil` `event_date` into `""` on retrigger** — `cmd/web-ui-api/handlers.go:149`, feeding a republished `event.Discovered` with an empty `EventDate` if the stored event never had one, which isn't valid `YYYY-MM-DD`. Likely low-impact in practice (the JSON field is presumably `omitempty`), but worth a quick check that downstream (telegram-notifier's message template) handles a missing date gracefully.

## Reviewed — downgraded / not acting on separately

- [x] **"Race condition in the pending-check transaction under concurrent retriggers"** (adversarial finding). Real in theory for two concurrent HTTP retrigger requests hitting the same event, since SQLite's default `BEGIN` doesn't take a write lock until the first write, so two transactions can both read `existingCount=0` before either inserts. In practice this only matters for the manual-retry path, and the fix above (skip the check entirely for `ReasonManualRetry`) removes the check-then-insert race for that path by construction — there's no longer a check to race on. The scraper-consumer path processes messages strictly one-at-a-time in a single goroutine per pod (confirmed by reading `consumeEventsDiscovered`), so it has no internal concurrency to race against itself. Not adding a separate DB-level fix (e.g. partial unique index) on top of the reason-based fix — would add complexity without a scenario left to protect against.

## Reviewed — no action needed

- [x] REST API contract (paths, methods, status codes, response field names), SQL parameterization (no injection risk), "update most recent pending row" matching logic, CORS wildcard (already an accepted no-auth cluster-internal design decision), env vars fully wired in the k8s manifest including `CORS_ORIGIN`, `computeStatus`/`listEvents` fixes from the previous round (deadlock and RFC3339 date parsing) — all confirmed correct.
